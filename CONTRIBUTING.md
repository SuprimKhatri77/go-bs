# Contributing

Thanks for considering a contribution to go-bs.

## Before submitting a pull request

```sh
gofmt -l .
go vet ./...
go test ./...
go test -race ./...
```

All of the above should be clean/passing. CI runs the same checks on every
push and pull request.

## Changing calendar data

Any change to `data.go` must include, in the pull request description:

- the affected BS year(s) and month(s)
- the source you used to verify the new value(s) — ideally something
  independently checkable (a live calendar, an official publication), not
  just another library's table
- an update to `knownPairs` in `convert_test.go` if you can verify a
  specific AD/BS pair for the year you're touching

`data.go` is generated by `tools/calendar-generator` (see that directory's
README) and carries a `// Code generated ... DO NOT EDIT` header — edit the
generator or its inputs, not the file directly, unless you're hand-patching
a single verified value and noting why in the commit message.

`TestExhaustiveBSRoundTrip`, `TestExhaustiveADRoundTrip` and
`TestCalendarDataIntegrity` will catch most internal inconsistencies
introduced by a bad edit, but they can't catch a wrong value that's
internally consistent — that's what the source citation above is for.

## Scope

This is a small, focused calendar conversion library. Please keep pull
requests scoped to that: conversion correctness, validation, documentation,
and tests. Frontend/UI code, additional calendar systems, or unrelated
tooling belong in a different project.
